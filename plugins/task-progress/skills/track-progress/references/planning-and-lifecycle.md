## 何时使用与模式选择

### 自动调用（Codex 主会话与 agent 均适用）

**任何任务开始前都先进行粗粒度规划。**在 Codex 主会话与 agent 开始实质工作前，先明确目标、主要阶段、依赖关系、执行者和验收结果；此要求覆盖所有任务，不依赖项目中存在 `AGENTS.md`/`agent.md`，也不要求用户点名。规划允许先按已知信息给出粗略版本，调查后再动态完善，不要为了等完整根因而先做实质实现。

任务包含 **2 个或以上** 可辨识阶段时，自动启用本 skill 并调用 Task Progress 跟踪，这是默认工作规则。先初始化或恢复任务网络，再把粗粒度阶段写入 HTN 子任务树；**不能只创建一个空的 root 节点就开始实现**。若初始化时尚未传入完整阶段，先调用 `decompose_task`；确认主要阶段、依赖和执行者后，再用 `get_ready_tasks` 判断哪些阶段可以启动。若任务确实是一个不可再分的简单操作，可保持为单一任务，不为满足形式而制造子项，但仍须在开始前形成简短计划。此规则覆盖主会话和 agent。

若 agent 收到的工作已由主会话的 Task Progress 任务树表示，沿用派发信息中提供的任务节点与尝试标识更新该节点，不另建重复根任务；若 agent 独立承担多阶段工作且没有可更新的父任务节点，则先粗略规划，再初始化、分解并维护自己的任务网络。单步查询或简单操作无需初始化任务树，但仍须先做一句话级别的粗规划。

多步骤新任务默认使用 HTN 任务网络：`init_task_network` → `decompose_task`（初始 tasks 已完成粗规划时可省略）→ 主会话首次 `render_progress` → `get_ready_tasks` → `update_task`。不得因任务看起来简单、顺序执行或不需要并行而改用线性 API。`init_progress` 对两个及以上步骤默认会被服务端拒绝；只有用户明确要求线性步骤时才可传 `legacy_linear=true`。

- 任务有子任务分解、依赖、并行、委派或重规划时，继续使用 HTN 任务网络表达结构与状态。
- 仅当用户明确要求线性步骤，或恢复已有旧版线性任务时，使用 `init_progress` → `update_step`；恢复时先 `get_progress`，再按原数据模式继续，不要求把旧状态迁移成网络。需要按步骤显示执行者、模型和思考强度时，在启动步骤的 `update_step` 调用中附上 `assignment`。
- **10 分钟拆分复核点：**任一仍在执行的 HTN 叶节点或线性步骤超过 **10 分钟**时，主会话必须明确评估“是否应拆成更细的任务展示”，不能只更新耗时而跳过评估。检查其中是否已有可独立执行、并行推进、存在依赖边界或可单独验收的阶段：有则把未完成工作拆成子任务并记录依赖；若当前仍是线性步骤且任务已适合分层展示，则按线性转 HTN 的规则重规划。评估后若没有自然任务边界，或细分不会改善执行与进度可见性，就保留原粒度，并在进度摘要中记下“拆分复核：无需拆分—原因”。overview 返回 `split_review_due_ids` 或写回执的 `split_review_due_count` 提示到期时，按需读取 tree/tasks 核对范围后，必须在继续常规工作或再次等待前处理：拆出可独立阶段，或记录具体的不拆理由。长命令/Dagu/CI 正在运行且不能安全中断时，不要为了拆分而终止它；保留原 attempt，同时拆出不会干扰它的独立阶段，或说明当前没有安全边界。**超过 10 分钟是强制评估点，不是自动拆分条件**；任务范围后来变复杂时，即使尚未达到 10 分钟也应重新评估。
- 线性任务转 HTN 时，不要在同一任务实例混用 `update_step` 与 `update_task`。在同一 `session_id` 下初始化 HTN 网络会把旧线性任务归档为历史；新网络沿用原目标，摘要已完成工作并保留其证据，只将未完成工作分解为新节点，避免把已完成部分伪装成待重做。若不值得转换，就继续原线性任务。
- 每个 Codex 会话复用一个 `session_id`。首次初始化可让工具生成并返回 ID；保存它，之后本会话的新任务必须显式传入同一个 ID，不为每个任务生成新 ID。插件按 `session_id` 隔离历史，换成新 ID 就会新建另一套任务记录，旧任务不会出现在新卡片的历史中。
- 恢复当前任务时调用 `get_progress({"session_id":"<本会话 ID>"})`，根据返回的数据模式继续执行，并保存当前 `task_instance_id`；不要调用初始化工具来恢复。
- 当前会话没有未收束工作或独立请求时，新任务使用 `init_task_network`；同一 `session_id` 下会归档旧任务并返回新的 `task_instance_id`。处理中收到的独立请求走 `route_request`，排队项用 `activate_request` 切换，不能用初始化跳过队列或原任务。不要为新任务生成另一套 `session_id`，也不要用 `rebuild_task_network` 代替独立请求登记。
- 若环境提供内置计划工具，可同步维护可检查清单；它不能替代插件中的实际状态。

### 开工前粗拆分与执行中动态补充（必须）

- **开工前先拆主阶段。**先把用户目标整理成若干粗粒度、可检查的结果阶段，并标明已知依赖和预计执行者。基于当前信息先建立可执行的第一版计划；调查中发现新约束后再调整。不要把代码调查、根因分析、实现、集成、验证、交付等明显不同的工作全部塞进一个长期 `running` root/leaf，再期望 10 分钟提醒替代最初拆分。
- **先有结构，再启动阶段。**多阶段任务调用 `init_task_network` 时优先传入主要阶段；若尚未传入完整阶段，立即用 `decompose_task` 建立结构。完成后调用 `get_ready_tasks`，只启动依赖已满足的 ready 叶任务。除非任务确实原子且无合理边界，否则 `root.children` 为空不能作为已完成规划。
- **粒度保持粗而有效。**按可独立推进、可单独验收或有清晰依赖边界的工作拆分，不把每个命令和微步骤都建成节点。可将同一缺陷下的调查与修复合并，也可将不同缺陷、独立审查、共享门禁拆成有依赖关系的阶段；门禁或资源等待本身不抹掉已存在的阶段边界。
- **执行中持续重看计划。**每完成一个主要阶段、收到用户新要求、遇到阻塞或根因导致范围改变时，对照剩余工作检查是否出现新阶段、依赖或验收项。发现后先在对应未完成分组下用 `decompose_task` 追加子任务并修正依赖，再开始这部分新工作；不要另建重复 root，也不要只把新增范围写进摘要。
- **阶段结束后盘点未闭环任务。**主会话在主要阶段真实结束（子智能体结果经复核后，或主会话阶段结束后）及开始下一阶段前，读取 overview 的 `stage_inventory_due`、`stage_inventory_due_count` 和 `stage_inventory_due_has_more`。overview 最多列出 20 个提醒；若 has_more，读取 root 的 `tree` 全部分页，收集有 `stage_inventory_due_attempt` 的节点，不能只处理前 20 项。无有效提醒时不调用盘点工具。
- **提交每个阶段盘点。**有提醒时读取完整任务树的所有未解决叶节点；注意 `depth_limited`，必要时从该深度的分组继续查询子树。固定分页的 `state_revision`，按需读结果/证据，并逐项判断继续、过期或被覆盖。对当前有效提醒调用 `review_stage_inventory`，传阶段 task_id、attempt_id、读取时的 expected_state_revision，以及每项的 task_id、decision（continue/obsolete/covered）和具体 reason（含证据或下一步）；没有未解决叶任务时传空 `decisions`。每次提交会改变 revision，处理下一个提醒前重新读取当前状态；并发变化时重读重审。盘点仅记录判断，不自动修改状态；保留历史，不伪造 resolved。并行工作可继续，不应中断真实运行的工作。恢复后先检查未处理提醒。
- **追加任务按真实依赖插入。**`decompose_task` 的每个新增问题节点填写非空 `addition_reason`，并用 `precedes` 指定依赖它的已有后继；同时用 `depends_on` 表示新增节点的前驱。服务端原子校验并更新真实依赖，面板按依赖显示；仅有前后顺序不代表依赖。已开始的后继不能静默插入前置，先协调执行者并使用显式重规划/重试保留历史。仅无依赖关系的任务保持原有相对顺序。旧客户端缺少原因时标为未记录，不补造原因。
- **尊重正在运行的工作。**若要拆分当前 `running` 叶节点，先协调其执行者停止或移交，再按本 skill 的 attempt 规则分解；不得为更新计划而中断不能安全停止的长命令、Dagu 或 CI。可先把不干扰运行门禁的独立后续阶段加到合适的未完成分组下；没有安全边界时记录具体原因，并在门禁结束后的第一个安全点重新拆分。
- **复核点是动态调整的兜底。**10 分钟 `split_review_due` 必须立刻处理，但它不能替代开工前粗拆分，也不能成为长期保留单一大任务的理由。记录“不拆分”时必须说明该任务为何不可独立推进或验收，而不只是“正在等待门禁”。

### 执行期间持续维护进度

Task Progress 是执行过程中的状态账本，不是只在开工时生成一次的计划。初始化和分解后，主会话须在后续工作中持续使用同一个 `session_id` 和当前 `task_instance_id`，直到任务收尾。

- **状态变化时立即更新。**开始一个工作块、实际派发子智能体、切换到另一叶任务、收到阶段结果、启动/完成较长命令或门禁、遇到阻塞、改变计划时，及时更新对应节点的状态与摘要。不要等到整项工作结束才一次性补记，也不要只在普通消息里汇报而不更新任务树。
- **切换主会话焦点时收束旧尝试。**主会话是单一执行者；开始处理另一个 `main_session` 叶任务前，先判断当前运行中的主会话节点是否仍有真实工作在继续。若只是暂时搁置、准备稍后回来，或主会话已经转去推进兄弟任务，就结束当前 attempt 并标记 `finished/open`，摘要写清已完成部分、剩余工作和恢复条件；恢复时用 `retry=true` 创建新 attempt。只有命令、Dagu/CI 或其他可独立继续的实际工作仍在运行时，才保留 `running`，并在摘要中记录运行 ID、等待结果和下一检查点。不能仅因计划稍后续做，就让主会话节点一直显示 `running`。子智能体的确切执行仍在后台时可保持其节点运行，并注明执行者和等待对象。
- **等待期间如实留痕。**Dagu、CI、构建或子智能体仍在运行时，节点保持 `running`；摘要记录当前运行 ID、已完成阶段和正在等待的结果。收到有意义的新阶段或终态后再更新，等待中不要反复写没有变化的摘要，也不能把“已排队/仍运行”记成完成。
- **继续执行前重新锚定。**长时间等待返回、上下文压缩/恢复、用户补充要求或插入请求结束后，先查 overview，再用 context 读取上下文与分页的 `session_work`，按需读取 tree/tasks，再继续或调整计划。不要因此另建重复根任务；独立新目标排队或建立并行实例，明确替换则先按用户要求收束旧工作。
- **执行提交与接受结果分开。**子智能体只更新获派节点并提交结果；`finished` 上报进入 `awaiting_review`，主会话复核证据后另用 `review_task` 接受或退回。主会话负责派发、协调、验收及根节点。未解决、失败或被阻塞时如实保留 `open`/`failed`/`cancelled`。
- **按真实执行回执收束。**子智能体返回终态后核对获派范围并提交其结果；主会话后续接手的独立工作另建明确分工的节点，不能把原子智能体的 running 摘要改成主会话正在执行的其他工作。缺少回执时保留未知并查询，不根据经过时长自动判定完成或取消。遇到待复核保护错误，读取 `review_status` 后调用 `review_task`，不要重复提交 finished 或另建无依赖的同范围节点绕过门禁。
- **汇报简洁但账本完整。**对用户只在关键变化时说明进展，避免重复播报；任务卡片则应保留足以恢复工作的当前动作、阻塞、验证状态和证据路径。
