# Cindy Hook coverage (0.1.140)

This directory is the Task Progress Cindy plugin source, with an additive Hook adaptation. `prepare.py` generates `core/` from the shared Task Progress implementation and Cindy patches. Do not edit `core/` as an independent source.

The manifest declares `will-compose-context`. It runs only for App initiated new turns in tasks whose owner selected this plugin as a context provider. The Hook attaches a short, read-only reference block based on a fresh internal `peek_hook_overview` snapshot for the exact Task Progress instance last returned by a successful tool call in that Cindy session. The snapshot reads persisted progress without reconciling executions or incrementing the view sequence. The hook rechecks the host-session and instance binding before attaching guidance. It can mention missing planning, pending review, actionable work-package synthesis, stage inventory, or root closure. It does not change the user's visible message or Task Progress state.

When no binding exists (including after an explicit clear), the Hook attaches a short startup guide: distinguish simple questions from multi-stage work, plan before substantive execution, and recover exact existing identities before continuing. An absent binding does not prove that no task exists; the guide must not cause guessed IDs or duplicate initialization. An invalid stored binding, unavailable KV/service, mismatched overview identity/schema, read-only instance, or no actionable reminder returns `allow` without a block. A resumed or failed turn does not imply task completion. Repeated composition may attach the same advisory again; no turn ID is available for a stronger replay key. The Hook never gates execution.

The server advertises `review_queue_v1` on overview and exposes a paginated `get_progress(view="review_queue")`. Submission items carry the exact attempt identity; synthesis items carry a source fingerprint, and pagination must pin `expected_state_revision`. These are state facts only: consumers must independently inspect results and evidence, never infer acceptance from a queue item. This endpoint does not by itself schedule a review.

Separately, an explicitly enabled session can request background follow-up after a successful state mutation. A durable reservation prevents duplicate dispatch; `dispatched` means only that the host accepted a follow-up, not that review passed. The watchdog re-reads the exact queue and reports items still pending without resending them. An uncertain delivery is never automatically resent; it can be released only after a complete revision-bound queue shows that exact obligation is no longer due. The host can revoke association when the plugin or app restarts, so a new user click may be required. This mechanism is fail-closed when identity, permissions, pagination, or delivery are uncertain and has not yet been verified against every host turn source.

Automatic follow-up scans the foreground task and discovered live parallel instances separately. Each reservation and ledger entry retains its exact instance identity; before sending a parallel batch, the adapter rechecks that the instance still belongs to the current foreground session at the same revision. The model must independently review the evidence. Native Cindy dispatch has not yet been verified for this implementation.

The internal `cindy_review_instances` read operation discovers the verified foreground and active or pending parallel instance identities from revision-pinned, bounded context pages. It returns no task contents and does not itself schedule or review anything. A truncated list is explicitly marked and must not be interpreted as a complete list of instances.

The internal `cindy_review_collect_session` read operation selects a batch from one discovered instance, keeping the selected and foreground instance identities separate. It requires the instance list and selected queue to have the same revision. Recovery reconciles an existing ledger entry for a verified parallel instance without changing the foreground.

One scheduling window reads at most 20 instance queues, then continues from the next instance at the same revision. A revision change restarts discovery; the temporary continuation is not persisted and cannot be used as proof that unseen work is absent.

The persisted opt-in does not certify a current host association. After the plugin runtime restarts, the sidebar reports that the association is unverified until a fresh user action or a successful host dispatch confirms it. Normal panel rendering and empty queue refreshes must not erase this warning.

When an enabled session is opened, the adapter first reconciles outstanding dispatches and then scans existing due work if it is safe to do so. It does not require a new task mutation to restart the scan. The host still enforces the session association; a permission denial disables follow-up and asks the user to re-enable it.

A complete, confirmed active-turn host event also starts a scan for an enabled session, including after a plugin restart with no session-switch event. Dropped, stale, incomplete, stopped and disabled states do not grant permission to dispatch.

Once its scheduler is started, an enabled idle session performs a read-only recheck at a 60-second interval so that state written directly by a supervised background worker can be discovered without a plugin tool event. This interval does not mark anything accepted or send a model turn when there is no actionable work. Opt-out, host suspension, delivery uncertainty and identity checks remain in force; host suspension requires a later confirmed active event to resume.

Immediately before dispatch, the adapter re-reads the selected obligation keys and verifies the exact session, instance, epoch and state revision. If the queue changed, it cancels the reservation without dispatch and retries the read a bounded number of times; explicit stop and binding are checked again after the read. A model must still recheck results and evidence because no client-side observation can atomically cover a later independent state change.

Positive identification of every selected key permits dispatch even if unrelated queue entries are unavailable or a scan window is truncated. The adapter reads at most 2,000 records per window and continues in later windows against the same state revision; a changed revision restarts the scan. This does not prove that any unobserved key is absent: recovery from uncertain delivery requires a complete queue read. Recovery checks at most five windows (10,000 records), and conservatively pauses if the queue exceeds that bound or any record lacks identity.

When a bounded recovery scan positively finds every selected key, the watchdog may still mark an overdue dispatched item as pending review. It cannot clear an uncertain delivery or infer the absence of any unobserved key from that partial scan.

Follow-ups are limited to 25 obligations per batch. After one batch remains pending for a minute, other distinct obligations may proceed; when two batches are still pending the plugin stops scheduling more and surfaces the waiting state. Explicit host stop, error, archive, deletion, user-interaction states, or dropped host events suspend new dispatches; an already queued host turn is not cancelled by the plugin. Observed suspension is also written to plugin KV and is cleared automatically only by a later confirmed active host turn. After a reported event gap, unsequenced activity cannot clear the suspension; when the gap has a sequence number, that number is persisted so the same or older numbered event cannot clear it after a plugin restart. KV can fail, so a restart still requires revalidation rather than an assumption that the session is active.

Cindy 0.1.143 keeps subscription sequence numbers in host memory and resets them on host restart or plugin removal. If that reset leaves an event-gap suspension in place, an explicit user re-enable clears the old sequence baseline but does not clear the suspension. A subsequent complete active event must have a host timestamp later than the user's re-enable; otherwise it remains suspended. A system clock moving backwards can therefore delay resumption, safely, until a later timestamp is available.

Stop, event-gap and recovery notifications are checked against the latest activity and settings generation before display. A delayed read or write must not replace a newer stop, resume or opt-out state in the panel.

Concurrent sessions share a single in-process host-call slot and a best-effort FIFO waiting queue. A session that encounters another in-flight call, an earlier waiter or the short cross-session cooldown releases its unsent reservation and retries later without consuming its rate-limit error budget. Disabled or stopped sessions leave the queue; stale entries expire after 60 seconds. The queue is not persisted across restarts. A known pre-run permission or rate-limit denial does not extend the cooldown. The host's own rate limit and restart behavior remain authoritative.


The manifest also subscribes to the `task-state`, `message`, and `session` topics. On `did-task-state-changed`, it asks the open panel to refresh only when the changed Cindy session is the active, mapped session. On `did-message-created`, only a saved assistant message with a message ID can trigger the same refresh; message content is ignored. The panel coalesces nearby events and rereads Task Progress through its existing read path. Neither event attests that a Task Progress attempt succeeded or ended. Missing or mismatched identity is ignored.

On `did-session-switched`, the existing handler reads the stored Cindy-to-Task Progress mapping, updates the active session, and tells the panel to bind to it. This session topic has narrower host coverage than the saved-message and task-state topics; it is not a turn-start or tool callback. No event is treated as a progress result.

The `message` topic grants the plugin access to saved message content even though this handler ignores it. Cindy 0.1.140 has no plugin layer equivalents of Codex `PreToolUse`, `PostToolUse`, or `SubagentStart`; their reminders, receipt association, and dispatch checks remain Codex only. `will-start-turn` also covers only App initiated new turns and adds no useful guidance beyond `will-compose-context` here.

## Diagnostics

Call `get_hook_diagnostics` from the target Cindy conversation with no arguments. The host-provided `session_context` restricts the result to that conversation. Each of the four event names has a delivery count and last receipt time; `did-*` receipts also retain the host event sequence and any `dropped` count. `will-compose-context` records receipt before state lookup and verdict delivery. Its `received` count is separate from `guidance_sent`, `guidance_not_sent`, and `guidance_send_failed`. `last_guidance.status` is `sent`, `not_sent`, or `send_failed`; sent entries include `kind` (`startup` or `current_state`), while other entries include a bounded reason code: `missing_hook_id`, `binding_invalid`, `binding_changed`, `state_unavailable` (KV/service failure or timeout), `overview_identity_mismatch`, `overview_unusable` (missing progress, read-only or incompatible schema), `no_actionable_reminder`, or `verdict_send_failed`. `sent` means the context verdict send completed, not that the host included it or the model followed it. Existing diagnostic entries are retained; old counts need not equal the sum of these new counters. Missing session identity cannot be attributed to a session, and unavailable KV can prevent diagnostic persistence. A diagnostic read has a 500 ms deadline. Once a whole-state PUT starts, the write queue stays serialized until the host confirms completion; an ambiguous failure leaves it blocked, while callers and the context hook have bounded waits. No exception text or context block text is stored. The diagnostic stores no message body, message ID, prompt text, or tool arguments.

While a PUT lacks confirmation, new KV updates fail promptly and queued updates that time out are discarded. A later successful confirmation restores writes. A rejected or permanently unconfirmed PUT leaves writes unavailable in this runtime; the host's whole-document last-write-wins API cannot safely establish that an unconfirmed write will never arrive. The hook remains fail-open.

This quarantine is held in the plugin runtime's memory. Simultaneous writes from independent instances sharing a KV scope are not supported.

For panel refreshes, compare `refresh_requested`, `refresh_ok`, `refresh_failed`, and `refresh_skipped`. A `read_ok` receipt includes the Task Progress state revision returned by the panel's `get_progress_view` call. Nearby message and task-state events may share one read but receive separate acknowledgements. `pending_refresh_count` means a refresh was requested but no panel acknowledgement arrived, for example because the panel was closed. A same-session switch reports `skipped_same_session` because it does not reread. `will-compose-context` adds model context and does not request a panel refresh.

These receipts prove plugin callback delivery and panel read completion, not that the task result was accepted or that a particular pixel was painted. Updating the plugin retains its KV diagnostics; counts start with the first callback observed by this version.

Build and install through Cindy Forge. Packaging alone does not activate the Hook. After installation, select Task Progress under the target task's context provider settings; enable `will-compose-context` for that task. Existing and other tasks are unaffected until selected.
