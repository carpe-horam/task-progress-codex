# Task Progress UX 优化设计 · 紧凑任务树修订稿

[打开修订后的交互稿](ux-v3/index.html) · [现有卡片实拍](ux-v3/assets/current-card.png) · [旧紧凑布局参考（修订 2）](ux-v3/assets/compact-tree-layout.png)

**本轮依据：用户反馈上一版“没有现在的 UX 一目了然”。** 上一版把任务清单放到“计划”页签，默认只展示当前工作，同时增加大面积留白和四视图切换，削弱了现有卡片直接看全任务的优势。本稿撤回这一方向；“概览 / 计划 / 结果 / 历史”四页签不再作为产品默认结构。

交互稿继续使用演示数据，不调用 MCP、真实 agent 或外部服务。场景/宽度/主题控制只用于预览。旧概览、窄屏和修订 2 紧凑静态图均为历史参考，含已撤销的结果分区；当前结构以 HTML 交互稿为准。

## 1. 设计结论

**保留现有卡片：标题、进度条、整棵任务树，以及“当前任务的历史计划”和“历史任务”两个独立折叠区。** 用户进入卡片就能看见做完哪些、正在做什么、后面还有什么，优化发生在这些信息的原位置。

1. 保留百分比和“已结束 / 总数”；旁边保留整体状态，明确区分执行结束与验收通过。
2. 常见 6–8 个任务默认全部列出；已完成项保留，当前项高亮，等待项直接写出前序名称。没有“先切换到计划才能看全”的步骤。
3. 保留父子缩进、树线和分组折叠；当前分支默认展开。点击某行只展开该行详情，不把其他任务换走。
4. 不新增大块概览、重复的当前任务卡或独立“下一步”卡。下一步就在当前任务后面的等待行。
5. 正常依赖等待叫“等待”，附“等待：检查兼容表现”；异常、用户输入和停止过程仅增加一条紧凑提示。
6. 已有刷新、导出继续放右上；暂停等新增动作放页尾/更多菜单，按状态显示。移除独立“任务结果”区，产出、未完成事项和检查记录归属对应任务项；整体结论在根任务内查看。两类历史仍各自折叠。
7. 维持原有深色紧凑视觉作为预览默认值，正式产品仍随宿主主题。Dagu 等执行服务只在实际来源详情出现，不成为界面主概念。

## 2. 修正后的取舍

本次审视依据包括现有 MCP Apps 卡片操作、源码与用户对首版设计的直接反馈。初版提出的“降低信息密度”“把模型和任务结构整体移到下一层”不再作为默认优化目标。

| 编号 / 优先级 | 保留的问题或需求 | 本次优化方式 |
| --- | --- | --- |
| UX-01 / P0 | 100% 执行结束不一定是任务成功 | 保留百分比，明确“项执行结束”；根状态单独写“最终验收 / 未解决 / 已完成” |
| UX-02 / P0 | 普通顺序等待被叫作依赖阻塞 | 行内改为“等待”，直接附前序名称；只有异常才突出提示 |
| UX-03 / P1 | 原因藏在两层展开里 | 将等待原因提到任务行，深层证据仍可按需展开 |
| UX-04 / P1 | 新稿把整棵树藏进页签 | 撤回四视图；任务树默认同屏可见，根/分组保留紧凑层级 |
| UX-05 / P0 | v3 需要暂停、恢复和停止 | 使用原卡片工具区/页尾与一行反馈，不增加独立操作面板 |
| UX-06 / P1 | 独立结果区重复任务树，产出与工作项脱节 | 撤销独立结果区，每项详情显示自身产出、未完成事项与检查；根节点只保留整体结论和定位链接 |
| UX-07 / P1 | 导出范围不明确 | 保留导出入口，点击后选择范围与格式 |
| UX-08 / P1 | 窄卡片需要兼顾密度与可读性 | 保持紧凑行高，正文 12–13px，辅助 11–12px，合理对比度；触控环境扩大命中区域 |
| UX-09 / P1 | 新稿合并两类历史，破坏原版清晰边界 | 恢复“当前任务的历史计划”和“历史任务”独立入口；分别按计划轮次和会话任务实例读取 |
| UX-10 / P1 | 刷新可能丢掉阅读位置 | 按稳定节点更新，保留展开、滚动和焦点；不因心跳重排任务 |

这次是本插件的设计取舍，不将一次反馈推广成用户对其他产品或所有界面的长期偏好。

## 3. 信息架构

### 3.1 默认卡片

```text
Task Progress                          导出  刷新  更多
修复图表坐标轴显示                     正在核验
67%                                      4 / 6 项执行结束
━━━━━━━━━━━━━━━━━━────────
计划第 1 轮 · 已解决 4 · 进行中 1 · 待执行 1

当前任务                                      6 个子任务
◇ 修复与验证                                      4 / 6
│  ✓ 复现坐标轴问题                               已解决
│  ✓ 确认修复方案                                 已解决
│  ✓ 实施代码修复                                 已解决
│  ✓ 检查相关回归                                 已解决
│  ● 检查兼容表现                                 进行中
│    验证助手 · 2 分 14 秒
│  ○ 整理交付说明                                    等待
│    等待：检查兼容表现

  ▸ 整体说明 · 根任务内
▸ 历史任务 · 2 项
执行状态更新于 14:32                       暂停新增工作
```

标准预览 620px，窄屏 360px，正式卡片跟随宿主可用空间。常见六项任务应在约 600–650px 卡片高度内显示完整任务列表；这是设计目标，需浏览器实测，不能用缩小到不可读字号来满足。

### 3.2 原位展开

| 内容 | 默认 | 用户展开后 |
| --- | --- | --- |
| 当前轮次任务树 | 所有直接子任务可见，当前分支展开 | 保留同级节点，原位显示目标、结果、证据与执行详情 |
| 已完成项 | 保留一行标题和状态 | 一次展开看到本项结论、产出文件和检查记录；点击具体记录查看，支持回到前序 |
| 正在执行项 | 高亮原行；执行者与耗时在第二行 | 查看实际配置、派发内容、运行标识和报告 |
| 等待项 | 显示标题、状态、等待对象 | 查看依赖及已有前序结果 |
| 未解决项 | 原行显示具体缺口 | 在本项查看部分产出、没完成的内容、未通过的检查及调整方案动作 |
| 根任务整体说明 | 嵌在根任务内，默认折叠 | 仅展示整体结论和完成范围；交付/缺口链接定位所属子项，不重复堆放全部材料 |
| 当前任务的历史计划 | 有旧方案时独立折叠、显示轮数 | 按轮次原位展开旧方案、调整原因、旧任务树及当时结果；不显示当前有效计划 |
| 历史任务 | 有归档任务时独立折叠、显示任务数 | 原位展开同一会话此前创建的其他任务；各自保留任务树、结果和此任务自己的历史计划 |

不把完整目标、模型参数、证据正文堆到每一行；但也不为隐藏这些详情而隐藏整张任务清单。分组收起由用户控制，运行分支不能因刷新自动收起。

### 3.3 两类历史的边界

沿用原版名称和层级。归属依据是会话、任务实例和计划轮次，不能按标题相似度、证据关联或方案调整来推断任务关系。

| 入口 | 包含什么 | 何时增加 | 不包含什么 |
| --- | --- | --- | --- |
| 当前任务的历史计划 | 当前任务以前被否决或被替换的旧方案，以及当时的任务树、状态和调整原因 | 同一目标调整方案；任务实例保持不变 | 同会话的其他任务、当前有效计划、单次执行重试 |
| 历史任务 | 当前会话此前创建并归档的其他独立任务 | 用户开始另一个任务；原任务归档，创建新任务实例 | 当前任务的旧方案、方案中新拆出的子任务、其他会话的任务 |

例如，同一会话先“整理本周读书笔记”，再“清理下载目录的重复文件”，之后“修复图表坐标轴显示”：前两个出现在**历史任务**。坐标轴修复的第一套方案未满足导出要求，改为第二套方案后，第一套只进入**当前任务的历史计划**，历史任务仍是两项。

```text
当前任务：修复图表坐标轴显示 · 计划第 2 轮
  当前方案的完整任务树……
  ▸ 整体说明 · 根任务内
▾ 当前任务的历史计划 · 1 轮
  ▸ 第 1 轮计划 · 已被替换
    调整原因、旧方案任务树、当时的结果与依据
▾ 历史任务 · 2 项
  ▸ 整理本周读书笔记
  ▾ 清理下载目录的重复文件
    该任务归档时的任务树与结果
    ▸ 此任务的历史计划 · 1 轮
```

两个区域是卡片中的同级折叠区，不将“当前任务的历史计划”放入“历史任务”内部。若旧任务本身也改过方案，它的历史计划仅嵌套在该旧任务下，使用“此任务的历史计划”。没有旧方案时不显示当前任务的历史计划区；没有历史任务时不显示历史任务区，不增加占位卡片。默认都折叠，展开状态互不影响，读取失败或分页也只影响对应区域。

旧计划是原位展开的只读完整快照，不缩减成一句“第 1 轮 → 第 2 轮”的变更通知。按最近归档/替换在前排序；点击“查看变化”定位当前任务的历史计划区。查看、导出不切换当前任务，不恢复旧方案，不增加任务或触发执行。

### 3.4 简单、并行与长任务

简单任务也列出全部三步，不只展示当前一步。并行时高亮多个运行行，继续保持计划顺序，避免按最近心跳跳动排序。深层分支用原有父子缩进与折叠；列表很长时自然滚动，并显示已结束/正在执行/待执行计数，不自动把已完成任务藏到另一页。

## 4. 状态语言与呈现规则

| 后端事实 / 场景 | 用户看到 | 主要动作 / 下一步 |
| --- | --- | --- |
| 没有任务 | 当前会话还没有任务 | 提示在聊天中描述目标；不创建重复输入系统 |
| deferred 节点正在规划 | 正在规划 | 展示正在确认的目标，暂无执行百分比时用文字 |
| 有有效 running 观察 | 正在执行 / 正在核验 | 当前工作与最近结果；可暂停新增工作 |
| pending，前序正常运行 | 待前序完成 | 说明“等待：兼容核验”，可定位该项 |
| 队列或资源尚未可用 | 等待执行资源 | 展示已知原因；未知排队时间不编造 ETA |
| waiting_user | 需要你选择 / 需要补充信息 | 单个具体问题及影响说明；提供选择后显式提交 |
| pause_requested | 已暂停新增工作，等待在途工作结束 | 仍显示 N 项运行；可请求停止在途工作 |
| paused | 已暂停 | 继续推进；说明恢复时先核对执行状态 |
| cancel_requested / stopping | 正在停止 | 保留运行项及已产出结果；不能提前显示已取消 |
| cancelled 且执行已结算 | 已取消 | 查看已保留结果；无自动恢复到运行 |
| 观察陈旧 / dispatch unknown | 执行状态待确认 | 核对状态；说明没有重复派发，不能以刷新成功代表执行存活 |
| 所有叶项结束但无有效根结果 | 正在最终验收 | 查看验收要求；不展示“已完成” |
| 有效根 resolved | 已完成 | 查看交付物；可导出结果 |
| 有效根 open | 本轮已结束，仍有未解决项 | 展示缺口、已有证据、可选后续；不使用成功色标题 |
| 正在建立新 epoch | 正在调整方案 | 展示为何调整、保留哪些证据和新增工作 |
| API 读取失败 | 暂时无法获取最新状态 | 保留最后有效快照、其时间及重试入口；不把任务改成失败 |

状态优先级：需要用户处理的事项 → 停止/暂停过程 → 执行未知或读取错误 → 实际当前活动 → 终态结果。多个状态并存时保留次要说明，例如“需要你选择；另有 1 项核验正在运行”。不得用一个 badge 擦掉其他事实。

进度条标签固定为“当前计划已结束的任务”，不表示时间进度或成功率。分母因分解/重建变化时显示一次“计划已更新：新增 2 项核验”，不尝试伪造单调百分比。所有失败/取消计入结束，但成功数只计有效 resolved 结果。

## 5. 关键交互

### 5.1 用户输入

只在后端明确请求输入时显示一行提示和处理按钮；点击后展开问题、原因、选项/输入与提交按钮，不默认把表单铺在任务树上方。选择不自动提交，不把推荐项当作默认批准。提交中防重复；成功后显示“已提交，等待任务继续”，不能直接跳成任务已完成。宿主不支持卡片提交时显示可复制的答复，交回聊天完成，不声称已发送。

### 5.2 暂停与停止

“暂停新增工作”直接请求暂停调度，已有执行继续收尾；返回 pause_requested 后显示真实在途数量。此可逆动作不加多余确认。

“请求停止任务”位于更多菜单。确认框说明影响范围、当前在途数量以及已完成结果保留；确认后请求停止，等真实终止观察再显示已取消。停止工具不受支持时显示“无法主动停止，等待执行结束”，不提供无效的强制终止按钮。

“继续推进”在 paused 状态可用，先恢复观察，再根据依赖/资源继续。不把浏览器刷新、打开卡片或重连等同于用户要求继续执行。

### 5.3 未知执行与错误恢复

分开展示“页面读取时间”和“执行状态确认时间”。点击“核对状态”产生读取/对账动作；结果未知时保留原状态和提示，不显示泛化的“恢复成功”。未知执行不能通过“重试”一键重复启动。可重试的确定失败显示重试范围；已验收或已被消费结果的重做走返工影响说明。

### 5.4 返工与方案调整

提交前展示具体变化：新增/替换任务、保留证据、失效验收、受影响后继、是否需要先结算在途工作。仅在确有范围变化或影响已验收结果时请用户确认；已授权的内部重新规划不一律增加批准步骤。执行资格由后端计算，界面不能靠勾选把失败任务变成功。

### 5.5 产出归属任务项

移除独立“任务结果”区域，不另建同级结果页或折叠区。每个节点同时承载这项工作的目标、状态与产出；展开一次就能看见本项做出了什么、还差什么，以及对应检查记录。

| 所属任务项 | 产出示例 | 检查示例 |
| --- | --- | --- |
| 复现坐标轴问题 | 复现步骤、输入材料 | 相同输入的复现观察 |
| 实施代码修复 | 代码修改说明、变更引用 | 修改范围核对；回归检查另属回归任务 |
| 检查相关回归 | 回归检查记录 | 对应测试的结果 |
| 检查兼容表现 | 兼容检查记录、对比材料 | 导出标签间距是否通过；未通过就在本项说明 |
| 整理交付说明 | 交付说明及对其他任务项的引用 | 说明是否覆盖范围和未完成事项 |

单项展开顺序：本项结论 → 目标/完成条件 → 产出 → 还没完成 → 检查记录 → 执行详情。无内容的区块不占位；待执行项明确“尚未开始，没有产出”，不生成空文件入口或默认成功记录。执行中可展示实际已有的草稿；未知、取消、失败状态不能据此推断已完成，已有产出按真实记录保留。检查入口直接位于本项详情，无需先进入全局结果区。

根任务内的“整体说明”只记录整个目标的完成范围、综合结论与未解决数，链接定位相应子项；不复制所有文件和检查清单。全部子任务结束仍不等于根任务完成，最终确认期间明确保留“整体任务仍在确认”。“查看交付”定位实际保存交付物的任务项；“查看未完成项”定位对应问题节点，并保持同级任务可见。

不是每个任务都必须额外创建“整理交付说明”节点。示例中它是实际交付步骤；如果成果已经分布在各工作项，则由根节点总结并引用即可，不为了补回被删除的结果区而制造一个汇总子任务。

点击文件或检查记录时，依据节点携带的引用读取其实际内容，绑定任务实例、计划轮次、节点和来源版本；不让不同任务项打开相同的通用示例。共用材料可以引用同一来源，但记录归属与采用范围必须明确。旧计划保留当时的节点产出和检查，不能在展开历史时查询当前同名节点代替旧记录。

### 5.6 导出

导出默认“当前任务摘要”，可选“当前任务完整记录 / 当前任务的历史计划 / 本会话历史任务”；格式按需选，不强制同时导出两种。说明是否包含完整派发文本、证据引用、历史轮次和导出时点。“当前任务完整记录”包含当前有效计划及该任务的旧计划；“当前任务的历史计划”只包含该实例的旧方案；“本会话历史任务”只包含其他已归档任务及各自历史，不夹带当前任务。只导出后端可确认的一致快照；失败保留选择，允许重新尝试。浏览器下载完成与实际文件可打开是不同验收项。

## 6. 视觉与可访问性

| 项目 | 设计值 / 行为 |
| --- | --- |
| 布局 | 延续原卡片；内边距 12–16px，行间用细分隔线和树线，避免大块空白和嵌套卡片 |
| 字体 | 系统中文字体；任务行 12–13px/1.5，辅助 11–12px，标题 17–18px；不依赖外部字体，允许缩放 |
| 主题 | 正式版本随宿主 light/dark 与其色彩变量；预览提供两种主题模拟 |
| 色彩 | 中性色为主体，绿色表示有效成功，蓝色表示活动，琥珀色表示需关注，红色只用于确定失败/停止风险 |
| 控件 | 桌面工具按钮 30–32px；任务行约 37–54px；触控环境扩大至至少 40–44px，图标按钮有可读名称 |
| 响应式 | 360px 起单列，标题和辅助信息可换行；详情原位展开，同级任务始终保留 |
| 可访问名称 | 状态有文字；进度条说明“执行结束”；按钮不依赖 hover 才解释效果 |
| 焦点 | 原生 summary 可用键盘展开；弹窗 Escape 关闭，回到来源；不在轮询时抢焦点 |
| 动效与播报 | 无装饰性持续动画；遵守 reduced-motion；只对重要状态/提交结果使用 polite status，不播报每秒计时 |

普通文字对比度至少 4.5:1，大字至少 3:1，按实际主题颜色检查；这是 [WCAG 对比度要求](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)。交互目标至少满足 24×24 CSS px 或允许的间距例外，本设计在触控场景使用 40–44px，依据 [WCAG 目标尺寸说明](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)。重要状态变化应能被辅助技术感知而不移动焦点，依据 [WCAG 状态消息说明](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)。这些目标不等同于已经通过完整无障碍审计。

## 7. 后端接线与一致性

复用已有 v3 API，不让 UX 另造状态机：

- `task_read.summary` 返回当前活动、等待原因、可执行的用户动作、根验收状态、计数及执行观察时间；UI 根据领域事实映射文案。
- 当前任务树随摘要读取；产出、未完成事项和检查引用通过对应节点的 `task_read.node` 投影按需读取，根结论使用根节点同一投影；不要求用户额外打开全局结果视图。历史按需读取。`task_history(type=task)` 读取该 session 的已归档任务；`task_history(type=epoch, task_instance_id=当前实例)` 读取该任务的旧计划。查看归档任务的旧计划时显式传它自己的实例 ID；分页游标绑定类型和实例，不能串用。浏览历史不会切换 session 当前实例，不影响真实调度。
- pause/resume/cancel 对接 `task_control`；输入使用新增设计的 `answer_input`，带问题 ID、问题版本、用户答复和来源；目标修订另按影响范围处理。动作必须有 scope、request_id 和预期版本。
- `available_actions` 由后端能力/状态给出；前端不能因为有按钮就假设具备停止、派发或验收能力。
- 旧版本缺少控制接口时保留只读视图，必要时回到聊天；不发送不存在的工具调用。
- generation/revision/view_seq 的排序沿用架构设计；轮询只更新读取状态，不更新执行心跳。
- 长内容分页，加载期间保留原布局；局部错误只影响对应区域，不清空全卡片。

## 8. 开发拆分与验收

| UX 批次 | 对应开发项 | 必须达到 |
| --- | --- | --- |
| UX-A：读懂状态 | A3、A5 | 结束/成功区分、普通等待非异常、完整任务树、稳定旧卡片 |
| UX-B：可控执行 | B3、B4、C2 | 当前活动/下一步、输入入口、真实暂停与停止状态、未知执行核对 |
| UX-C：结果和返工 | C1、C2、C3 | 交付物/缺口/证据关联、方案变化影响范围、预算收尾 |
| UX-D：长期使用 | D1、D2、D3 | 历史分页、按范围导出、主题/窄屏/键盘、安装后的空态与错误态 |

本稿增加以下 UX 验收项；与原 T01–T34 / E1–E7 并行引用，不覆盖其编号：

| ID | 验收任务 | 通过条件 |
| --- | --- | --- |
| U01 | 进入正在执行的卡片 | 无页签切换即可看到全部常见任务、完成项、当前项与下一步 |
| U02 | 查看普通依赖等待 | 摘要直接说明等待对象；无“需要处理”的错误暗示 |
| U03 | 所有叶子结束但根未验收 | 没有绿色“已完成”，清楚展示最终验收仍在进行 |
| U04 | 提交输入、暂停、恢复、取消 | 请求状态与执行事实分开；不重复提交、不提前释放资源 |
| U05 | 页面刚刷新但执行观察陈旧 | 两个时间不混同；核对未知时不自动重派 |
| U06 | 展开不同工作项找产出、检查和缺口 | 没有独立结果区；一次展开对应项即可看到其内容，记录链接绑定正确节点；待执行无伪造产出；根结论不提前完成；定位后其他任务仍可见 |
| U07 | 同会话不同任务与同任务改方案 | 两个同级入口：旧方案仅进入当前任务的历史计划，历史任务数量不变；新任务才归档原任务；旧任务自己的计划不混入当前；展开/分页/导出互不串用且不改变执行 |
| U08 | 360px 容器、长标题、200% 文本缩放 | 主要任务与操作不横向溢出，不因截断丢失关键状态 |
| U09 | 键盘与读屏使用 | 节点、折叠区、弹窗可达；焦点可见并保留；不反复播报计时 |
| U10 | 数据乱序、断连、读取失败 | 保留最后有效快照，状态不倒退，重试不创建新任务 |
| U11 | 查看导出范围后导出 | 范围、格式、时间明确，文件与所选快照一致 |
| U12 | 未连接任何队列服务 | 正常显示/操作宿主执行任务，无 Dagu 安装引导或依赖 |

建议后续用 5 位目标用户做理解与操作测试，记录是否能正确判断当前状态和下一步、点击次数、错误操作和发现缺口的时间。样本规模和指标是研究计划，本次不报告虚构的成功率。

## 9. 原型与验证边界

历史示例特意采用读书笔记、下载目录清理和坐标轴修复三个不相关目标。选择“12 · 方案已调整”，可同时看到两个独立历史入口，并展开旧计划的任务树。普通第 1 轮场景无历史计划入口，与原版无旧方案时的行为一致。

本修订稿以任务树同屏、原位展开为验收方向；旧四视图的 56 组合检查不作为当前稿通过的证据。交互稿用于评审信息层级、状态语义和操作路径。包含常规执行、短任务、需输入、暂停过程、已暂停、停止过程、已取消、未知执行、最终验收、完成、未解决、方案调整、空态及读取失败场景；可切换窄屏和主题。

演示中的确认、结束和恢复不会调用真实任务。设计预览将“模拟执行观察”放在独立预览栏，不能将该控件带入正式产品。验证记录见 [预览验证记录](ux-v3/validation.md)，真实 MCP 控制、完整辅助技术与后端接口验收仍在开发阶段完成。
