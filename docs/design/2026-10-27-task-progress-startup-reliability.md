# Task Progress 开工规划可靠性：研究与实施方案

日期：2026-10-27（Asia/Shanghai）

状态：研究完成，方案尚未实施；没有修改产品代码或用户 hooks 配置。

## 结论

建议把“任务开始前先规划”做成由 **宿主启动提醒、一次提交粗计划、服务端规划状态校验、工具调用前检查** 组成的流程。只继续加长 SKILL.md，不能可靠解决完全漏用插件的问题；只在服务端拒绝空 root，也不能约束从未调用插件的 agent。

本次发现了比“模型忘了”更具体的产品原因：skill 要求先拆分，但工具初始化却把未拆分的 root 告诉模型为 `ready`，工具描述还明确写了“根任务默认 ready”。两条可见规则不一致。应当把规划是否完成与任务是否可以执行统一成服务端契约。

用户要求覆盖所有任务。对应设计是：任何工作先判断粒度；多阶段工作建立粗任务树，单步工作记录简短计划或轻量豁免，纯文本简单问答无需产生任务卡片。后续根据阶段结果和新要求动态补充。

### 2.1 自动选择仍依赖模型

官方机制先给模型 skill 名称、简介和路径，决定使用后才读取正文；`allow_implicit_invocation=true` 表示允许自动选择，不是每轮强制执行。目录可能缩短简介。[官方 Skills 文档](https://learn.chatgpt.com/docs/build-skills)

当前正文有 216 行、15,091 字符。关键约束位于正文，但本次 agent 没有读取正文。继续在正文中增加“必须”，对正文未被加载的情形没有直接帮助。

### 2.2 初始化返回的状态与 skill 不一致

`server.py` 当前实现：

- `_new_network`（约 335 行）只创建空 root。
- `_node_is_ready`（598 行）仅检查无子节点、pending、依赖满足；空 root 自动 ready。
- `init_task_network`（728 行）立即持久化该网络并返回。
- `update_task`（854 行）允许这个 root 启动执行。
- 初始化工具描述（1668 行）明确告诉调用方“根任务默认 ready”。

所以即使 agent 已选中插件，只看工具描述也会走到“初始化 → 展示 → 启动 root”，与 skill 中“先 decompose_task → get_ready_tasks”冲突。

### 2.3 提醒只能在插件被调用之后出现

当前 MCP 初始化响应未提供额外 `instructions`，插件没有生命周期 hooks。10 分钟拆分提醒只在读取/更新进度时计算；完全漏用插件时，不会有服务端调用来送出提醒。给 MCP initialization 加 instructions 可作辅助，但仍需实测宿主如何使用，不能替代生命周期入口。

## 4. 推荐的实现

### 4.1 精简 skill，将启动规则放到最前面

保留 skill 名称，避免无谓迁移。建议简介开头直接表达：

> 任何多阶段任务开工前先规划和拆分。用于实现、修复、研究、审查、合并 worktree、验证和提交 PR；执行中持续调整任务树。

正文首页只保留启动、恢复、执行、收尾四步及简短例子；attempt、重试、依赖失效等详细协议移入 references，相关操作再读取。

明确 `task process`、`task progress`、`任务进度` 的常用别名。已有工作目标时，“打开 task process”默认指当前进度面板；只有用户明确说项目或仓库才按项目处理。打开已有面板走读取/展示，不重新初始化任务。

精简能改善选择与执行成本，但它只是一层辅助。官方也建议分别测试显式调用、隐式触发、带干扰上下文的触发以及不应触发的反例。[Skill 评估方法](https://developers.openai.com/blog/eval-skills)

### 4.2 让新任务一次提交粗计划

优先扩展现有 `init_task_network`，加入 `tasks` 与幂等请求标识，避免把原本连贯的规划拆成多个容易漏掉的工具调用。

新契约：

1. 在内存中验证标题、子任务、执行者、依赖和节点 ID；多阶段任务必须有至少两个有实际结果边界的阶段。
2. 验证成功后，在同一 session 锁内一次保存 root 和子任务，并归档旧任务。
3. 响应给出当前实例、ready 叶节点和简短 `next_actions`。可直接启动指定 ready 叶节点，不要求为了形式再读一次完全相同的数据。
4. 请求重试不能再次归档或生成重复任务；相同请求标识返回同一结果，相同标识但不同内容返回冲突。
5. 同一宿主会话开始新任务时，使用期望的旧实例/版本做并发校验，避免两个并行初始化互相覆盖。

兼容的无 `tasks` 初始化只创建 `planning_status=required` 的草稿，返回 `next_actions=[decompose_task]`；它不能声明 root ready。

### 4.3 服务端把“规划完成”与执行状态分开

增加明确的规划状态或等价标记，而非靠 `children=[]` 猜测：

```text
required --有效粗拆分--> ready --启动 ready 叶任务--> executing
required --明确单步理由--> atomic
```

约束：

- 新的多阶段任务规划未完成时，`get_ready_tasks` 返回空列表及原因。
- `update_task(..., running)` 在同一锁内验证规划状态；未满足返回稳定错误码 `planning_required` 和下一步参数提示。
- root 是协调/验收节点，不因“暂时没有 children”就能开始执行。
- 真正单步的已跟踪任务允许显式 `task_kind=atomic` 和具体理由；不能用“时间紧”“顺序执行”“正在等测试”作为多阶段任务的通用豁免。
- 图结构验证只能保证形式正确，不能证明拆分有意义；“开始、完成”这类空洞阶段还需行为评估。
- 普通状态修改不触发展示。规划中、错误、恢复状态都必须有可见说明，不能再通过隐藏整个页面表示。

这层保证的是插件内部状态正确；它仍不能发现从未调用插件的 agent。

### 4.4 插件携带轻量启动 hook

使用本地 command hook 提供启动上下文，减少对 MCP 连接就绪时机的依赖。脚本复用插件的 Python 启动器，只做有界本地读取，建议 timeout 2 秒，不请求外部模型。

以下是候选行为设计，不是已经配置的功能：

| 事件 | 建议行为 |
| --- | --- |
| SessionStart：startup/resume/compact/fork | 提供简短开工约束或恢复锚点；fork 不复制父会话的可写任务归属 |
| UserPromptSubmit | 提醒先判断“新目标/继续/补充/单步”，提供已有任务实例；不要每条消息都新建任务 |
| PreToolUse | 检查本轮是否有有效计划、已有任务继续标记或单步豁免；必要时先返回明确补计划动作 |
| PostToolUse（仅相关规划工具） | 从成功结果建立/更新宿主会话与插件任务的映射；失败调用不解锁 |
| SubagentStart | 提醒沿用派发节点，仅维护自身状态；不创建或展示主会话 root |
| Stop | 已绑定任务仍未收尾时做一次有界提醒；不无限阻止结束或用户中断 |

建议注入内容控制在约 150–250 tokens：当前任务引用、必须做的动作、skill 路径。不要把 15,091 字符正文在每个工具调用前重新注入。

hook 自身不创建任务树、不调用 render_progress、不打开标签页、不猜测任务完成。规划内容仍由理解用户目标的 agent 产生。

### 4.5 首次实质工作前的检查

提供两种透明模式，不能把提醒模式标成强制保证：

- `guided`：启动提醒 + 插件内部规划校验；缺少完整宿主接入时使用，明确显示只提供提示。
- `required`：在 hook 已信任、映射有效、运行环境覆盖已验收的情况下，要求每次开始新工作先提交计划或显式的单步判断。对本用户“任何任务开始前先规划”的偏好，推荐最终采用此模式。

`required` 模式不是简单“所有工具都禁止”。规则和 skill 读取、用户引用会话的必要读取、工具发现、进度工具、澄清问题和安全终止操作属于启动准备。放行范围必须狭窄、可审计，混合 shell 命令不能因为含有 `cat`/`rg` 就被当成只读。

对没有任务树的真实单步工具操作，可增加轻量 `acknowledge_work(kind=atomic, summary, reason)`；它只记录本轮粒度判断，不创建假子任务或弹出 UI。纯文本简单问答无需调用该工具。已有任务的后续消息读取并确认继续即可，不重复初始化。

缺计划时，在**受支持的工具执行之前**返回明确原因及可用的计划入口。不要依赖自然语言错误被模型自己理解，也不要把 `continue:false` 当成 PreToolUse 的阻断格式。被拒绝后不能执行原工具；错误分支也不能把失败标为成功。

插件关闭、未信任、连接失败或状态文件损坏时，进入可见的降级状态，保留用户工作可继续恢复的路径；不以不断报错制造死循环，不宣称此时仍有强制保护。用户中断始终允许。宿主未覆盖的工具只能靠提示和验收来约束，不能承诺 100% 首工具前拦截。

## 5. 会话身份和恢复是必要条件

当前插件 `session_id` 与 Codex 会话 ID 不同。本例分别是 `a9c0103d-7701-4408-8ba8-ddfdda064ff5` 与 `01a17c12-2c30-78b2-891d-0a51b3235f0e`。只凭 cwd 找当前计划会把同一仓库的多个会话混到一起。

建议采用独立绑定表：宿主 session/turn、插件 session/instance、规划契约版本、最近确认的状态、提醒去重键。由收到真实宿主事件的桥接层记录映射，不能把模型自己传的 `codex_thread_id` 标为宿主验证。

MCP server 与 hook 必须使用相同的状态路径规则、锁和原子写入。hook 默认只读取权威状态；不要各维护一套互不一致的“已经规划”布尔值。每次解锁都核对当前实例与规划版本，避免旧任务的有效计划放行新任务。

子智能体可能共享父 session ID，不能只凭该字段认定当前执行者就是主会话。必须结合派发节点/attempt 与可验证的 agent/turn 关联；角色信息不足时不自动绑定主 root，也不阻止所有子任务。该路径在真实宿主验收前保持提示模式。

继续、压缩恢复、任务补充时复用当前实例；新增范围先补入计划。10 分钟复核仍在下一次可用生命周期事件或进度调用时触发，不是假定拥有后台定时器。长期外部命令运行时，记录 run ID、等待对象、下一检查点；不要为了满足拆分门槛终止真实 Dagu/CI。

旧数据迁移采用显式版本：新任务执行新契约；已有 running 的空 root 不自动取消、归档或伪造新开始时间。提示主会话在安全点补计划，保留外部执行和既有证据。补记完成阶段时要区分实际执行时间与记录时间。

## 6. 安装、诊断与交付顺序

1. **P0：统一工具契约。**增加原子粗计划入参、planning_required 校验、幂等保护；精简 skill 与工具描述。先消除“空 root 已 ready”的矛盾。
2. **P1：宿主入口。**插件内增加 hooks、会话绑定、恢复提示、状态诊断；在真实桌面会话观察 hook 触发及初始计划。默认先观测提示路径。
3. **P2：启用 required。**在工具覆盖、bootstrap 放行、单步豁免、子智能体和降级矩阵通过后启用首次实质工作前检查。
4. **P3：防止执行中遗忘。**补阶段切换、超时复核和收尾检查，保持提醒有界且不抢 UI 焦点。

安装后要分别展示：插件已安装、skill 可见、hooks 被发现、hooks 已信任、最近实际触发、当前约束模式。单次缺少 heartbeat 只能记为未观察到，不能推断已禁用或已信任。宿主 hooks/list 可为诊断工具提供权威的注册/信任状态。

不能通过直接写 `trusted_hash` 或添加绕过信任参数让交付“看起来完成”。插件更新后还需核对所加载的代码及信任状态。公开目录与本地桌面分发的 hooks 规则不同；当前实现应优先按本仓库的桌面本地插件交付，并在发布前重新核对对应渠道。[Claude 插件迁移说明](https://developers.openai.com/plugins/guides/submit-claude-plugin)
