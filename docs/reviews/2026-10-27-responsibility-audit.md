# 主会话与子智能体职责边界审查

日期：2026-10-27。基线：`52f7b19abc452ce1bf2aa7cd23485df7db2028f6`，版本 **0.2.0**。本轮仅审查与隔离复现，未修改产品代码、已安装插件或后台服务，未提交新代码。

结论：当前实现可以保存“谁被标记为执行者”，但没有完整表达和约束“谁负责规划与派发、谁上报执行结果、谁接受结果、谁验收整体目标”。skill 写出了职责规则，服务端尚未把它们落实为独立状态和校验。真实分工可以由主会话遵守指令实现，但无法从现有账本可靠核验，也不能依赖现有 API 阻止职责混用。

## 提示、显示与本会话中的实际记录

- skill 的职责原则明确：主会话统筹、派发、集成和验收；子智能体仅执行派发范围。这是合理规则，但 `update_task` 没有独立的“上报者/验收者”参数或存储。
- hooks 主要提醒先规划，只有 fork 分支提示不要假定父任务所有权；没有核验实际执行角色或派发范围。hook 提示也不能代替服务端状态校验。
- UI `executionSummary` 主要展示主会话/子智能体、模型和思考强度；attempt 展示执行配置或分组综合验收。叶任务没有独立的执行提交与主会话接受记录可供展示，不能只靠改标签解决。
- 本会话此前的 `service_installer` 确实做过子智能体派发，主会话也复核过结果；但持久化记录只有一个 `execution_mode=subagent` 的 execution attempt，`agent_name` 为空，没有独立验收者字段。主会话当时的记账不完整，现有协议也未阻止这种情况。原记录未被回填或改写。

这些观测及源文件 SHA-256 见 [workflow-observations.json](2026-10-27-responsibility-evidence/workflow-observations.json)。

## 主会话承担过多实现工作

用户补充的这一点与验收角色混用有关，但需要单独修正委派决策。不能只补一个主/子角色枚举，然后继续让主会话执行大部分复杂任务。

本会话共享后台改造的 7 个叶任务中，5 个标记为主会话执行，2 个标记为子智能体执行。这一比例本身不衡量工作量，但其中“实现共享 HTTP 协议、认证和单实例生命周期”明确是复杂且可划定文件边界的实现任务，却留给了主会话；实际分工因此也存在偏差，不能全部归因于插件。设计决定和最终验收可由主会话承担，HTTP 实现及相关回归本可作为完整交付块委派，安装器作为另一块委派。

当前规则的三个诱因：

- 把“能否并行”和“应该由谁执行”混成一个决策；不能并行不代表应由主会话完成。
- 把强依赖和共享文件冲突当作主会话自执行的通用理由；很多情况下应整条依赖链交给同一 agent，或串行派发并指定文件归属。
- 把“实施”与“集成”绑在一个 main_session 示例中；主会话的集成责任因此容易扩展为自己编写复杂实现和全部验证。

建议的默认分工：

| 工作 | 默认执行者 |
| --- | --- |
| 明确目标、拆分交付边界、安排依赖、协调资源、跨任务取舍 | 主会话 |
| 深入排查、复杂实现、多文件改动、专门验证、独立评审 | 子智能体，必要时整段顺序执行 |
| 接受或退回子任务结果、综合判断是否满足用户目标 | 主会话 |
| 短小、低风险且交接成本明显高于执行成本的操作 | 主会话可自执行，并记录原因 |

这里的“复杂”应依据工作性质和验证范围，在规划时判断，而非等主会话做了 10 分钟才补派发。主会话接回子任务应是显式的接管决定；失败或需要修改时，优先把具体反馈交回同一 agent。若确实只能由主会话完成，记录不可交接的具体原因，不能仅填“有依赖”“需要集成”或“需要上下文”。

优先修正 skill、示例和规划结果中的默认分工，并为主会话承担复杂执行任务要求可检查的自执行理由；与此同时修复实际派发绑定。完整的执行结果/验收状态分离仍然必要，但不必等待可信宿主身份接入，才开始纠正复杂工作默认落到主会话的问题。

## 修复应落到状态与动作

建议保留主会话负责整体工作的原则，同时将下列事实分别记录并校验：

1. **计划责任**：任务负责人、计划执行者、主会话是否决定自执行。复杂分析/实现/验证默认委派，独立于能否并行；主会话自执行需要具体理由。计划执行者不能被启动参数覆盖；接管或重新分配必须有显式动作、理由和历史。
2. **真实派发绑定**：准备派发时记录任务、attempt 和派发请求；实际工具返回后通过专门动作绑定 agent ID。派发失败必须有终态。不可把未知 ID 预填为真实回执，也不可为补字段制造一次虚假重试。
3. **执行结果**：子智能体提交本节点的结果与证据，进入待主会话验收状态。该结果不能仅凭自身的 resolved 声明触发默认依赖放行。
4. **接受或退回**：主会话单独记录接受/退回及理由，绑定具体执行 attempt 和结果版本。接受后才满足默认依赖；子任务重试必须使旧验收失效。
5. **整体验收**：父/root 综合验收保留独立记录，并检查声明角色。存在 open/failed 子结果时须显式处理、重试或记录可解释的豁免，不能空记录完成。
6. **协调指引与 UI**：按当前状态返回主会话待派发、可自执行、待复核、待综合验收等动作；子智能体只收到其绑定范围内的工作。界面分别呈现计划、派发、执行提交和主会话验收，不将它们压成一个执行者标签。

主会话仍可执行适合自己处理的叶任务，但该次执行应与整体协调、子任务验收职责分开记录，不能通过一律标记 main_session 省略分工决策。

## 身份与权限边界

当前共享 HTTP 的 Bearer 证明请求持有该用户的服务凭据，**没有证明请求来自哪个 Codex 主会话、thread 或子智能体**。`execution_mode`、`agent_name`、thread ID 等都是调用方填报；instance/attempt ID 主要防止旧结果覆盖，且可通过进度读取获得，不是角色授权凭证。

因此，本轮证明的是“服务端接受 subagent 声明来做父级验收”，没有把它夸大成经过宿主认证的真实越权调用。只新增一个自报 `caller_role=main_session` 同样不能提供可信权限。

业务状态约束可以先实现。若要保证只有特定主会话能验收、只有获派 agent 能改特定节点，还需要可信宿主身份/派发回执，或可信协调方签发并限定 session、instance、node、attempt 的能力凭证。插件也只能约束经它记录和放行的操作，不能仅靠进度工具阻止模型在其他工具中自行做工作。

先前通过的 108 项回归不等于这些职责门禁已经存在；当前 `test_synthesis_requires_and_persists_execution_metadata` 验证的是验收元数据的保存，未验证 subagent 声明被拒绝。实施修复后，应把本轮发现转为正式拒绝/允许场景的回归测试，再验证 UI 与旧历史的兼容性。
