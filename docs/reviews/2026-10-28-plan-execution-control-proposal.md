# 主会话与 Task Progress：可恢复的任务执行协议

2026-10-28。依据历史会话审查、两路研究和用户确认的职责边界；本轮实施结果另见文末验证记录。

## 决策与职责

主会话负责理解用户目标、拆分和编辑任务、分配执行者、调整计划、复核结果。Task Progress 保存这些决定和执行事实，检查状态转换，并据此给出下一步引导。子智能体执行限定范围，提交证据，由主会话验收。

用户认可的补充约束：

- 恢复信息不能只有标题和百分比，还包括原始请求、目标、约束、验收标准、已完成证据、未解决项和恢复位置。
- 可以调整或重规划，但不能抹掉正在运行的执行、既有结果或验收事实。变更保留理由；继续有效的旧结果要引用来源，需要重做的结果不能沿用旧验收。
- 一个任务完成和整个会话工作已处理完毕是两个状态。插入请求完成后，仍须检查原任务和队列。
- Task Progress 的提示和服务端校验有用，但不等于宿主强制调度；用户明确停止或取消始终优先。

## 为什么有计划仍然漏执行

历史证据表明，待验收提交没有及时被主会话消费，后继任务被正确阻塞；随后重复提交 finished、另建节点或重新初始化，反而使任务列表更难理解。另一类情况是子智能体实际已结束，但对应节点没有收束，且被主会话后续工作混用。不能仅依据 running 或百分比断言工作从未执行。

必须区分：确实遗漏、执行了但未记账、结果待验收、旧计划已失效、外部执行仍在等待、缺少足够回执。恢复时先对账，不按运行时长猜测完成，也不盲目重跑有外部副作用的操作。

## 新消息的分流

| 用户消息 | 主会话处理 | Task Progress 记录 |
|---|---|---|
| 当前目标的补充、修正或新验收条件 | 更新当前目标与计划 | 同一实例的上下文、追加阶段或重规划及理由 |
| 状态询问、简短问答 | 答复后继续原任务 | 通常无需新任务；保留恢复位置 |
| 无关的独立任务，暂不适合并行 | 登记排队，继续当前任务 | 原文、目标、约束、验收、入队理由和 FIFO 顺序 |
| 可隔离的独立任务 | 建立独立实例，由子智能体执行 | 独立实例、尝试、派发、验收和返回原任务锚点 |
| 明确停止、取消、替换原目标 | 服从用户指令，协调在途执行后如实收尾 | 不以“排队”抵消用户取消；不把部分完成写成已解决 |

分流由主会话根据用户意图判断，不由字符串关键词自动决定。并行需要范围、文件和外部资源可隔离，也需要实际可用的子智能体容量；否则排队。登记并行请求不等于已派发，登记队列不等于正在执行。此能力不额外授权发送消息、发布或其他外部操作。

## 当前实现范围

会话保留一个当前主任务，并持久保存独立请求注册表。并行任务有自己的 task_instance_id，在同一 JSON 文档和会话锁下原子写入；其更新不会替换当前主任务。归档主任务时不递归复制整个注册表。

- `route_request` 登记独立请求，显式选择 queue 或 parallel，保留原文、理由和验收条件；相同 request_id 安全重试，不同内容冲突被拒绝。
- `activate_request` 在当前主任务已完成或已如实终止后显式激活 FIFO 队首。切换和归档使用一次原子写入。
- `update_request` 调整尚未启动的排队请求并保留变更记录；`cancel_request` 只能取消尚未执行的请求，不能假装停止外部执行者。
- `update_task_context` 保存当前实例的目标、约束、验收标准和恢复位置，记录修改理由。重规划保留上下文与历史证据。
- 现有分解、执行、绑定、复核和重规划接口按显式实例隔离并行任务；并行叶任务由子智能体执行，父级验收仍由主会话完成。
- `session_work` 告诉主会话当前主任务、队列和并行请求、返回位置、下一步及会话是否还有待处理工作。它不自动运行任务，也不唤醒闲置聊天。

当前结构调整沿用 `decompose_task`、`reassign_task`、`rebuild_task_network`；本次不增加任意修改已执行节点的接口。抢占式暂停、多队列优先级、自动调度和宿主事件接入不在本轮实现中。

## 恢复与推进循环

1. 新一轮、压缩恢复、等待返回或插入请求完成后，读取同一 session 的当前进度与 session_work。
2. 读取 task_context，并检查真实在途执行、未绑定回执和待验收结果；必要时查询执行者。
3. 对照用户最新要求调整目标或计划；独立请求进入队列或独立并行实例。
4. 处理阻塞关键路径的验收，再执行依赖已满足的任务。一个无关任务待验收不应全局阻塞所有独立工作。
5. 完成一个请求后重新读取当前主任务与队列。当前主任务尚未结束则返回；已如实收尾则继续队首。未解决结果要明确报告，不包装为成功。

恢复说明应具体，例如“前两份报告已验收；下一步完成请求隔离回归，再安装；原 visual-diff 会话只读审查，不代其接受结果”，而不是“继续之前的工作”。旧记录没有原文或验收证据时保持未知，不从摘要补造。

## 进度展示

用户截图中两份报告已提交、尚未验收，第三项尚未开始。旧界面显示 66% 执行结束，用户无法直接判断完成了什么。对应的验收完成度实际是 0/3。

新界面以按当前协议完成验收的已解决叶任务计算主进度，分列待验收、执行中、未开始、未解决与旧记录验收未知。每个叶任务直接展示状态和产出摘要。根任务综合验收单独展示，叶任务 100% 不代表整体已交付。排队请求不进入当前主任务的分母，并行请求单独查看，不能悄悄替换主卡片。

## 后续更强约束的路线

先验证插件本身的状态与恢复协议，再考虑接入真实执行事件。可逐步引入动作领取、可信回执关联和对账；必须区分执行事实与业务验收，工具成功或 agent turn 结束不能自动接受任务结果。

Codex 官方文档提供生命周期 hooks，包括工具前后和结束检查，但存在覆盖与失败处理边界；实际桌面版本、信任状态及具体工具路径需要逐项验证。PostToolUse 不能撤销已发生的操作，Stop 也不等于闲置唤醒。[官方 hooks 文档](https://learn.chatgpt.com/docs/hooks)

App Server 提供执行和 turn 事件，可作为后续回执来源；自行运行的客户端不代表已经接入当前桌面聊天。[官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)

建议顺序：先只观察并测量遗漏、记账延迟和误判；再针对已覆盖的工具启用有限前置约束及有界结束复核；只有这些不足以满足要求时才考虑完整宿主调度层。不能因为插件不可用而无限阻止用户退出，也不能在未知执行结果时自动重复外部动作。

## 验收场景

- A 运行时登记 B，A 的实例、节点和 attempt 不变。
- 并行 B 提交、复核或完成，都不把 A 或整个会话标成完成。
- A 如实收尾后只能激活队首；重复登记和未知结果重试不重复建任务。
- 同名节点在两个实例内互不覆盖，旧 attempt 和已清理实例的迟到写入被拒绝。
- 压缩恢复所需信息来自持久状态；重启、重规划和切换后队列、原文与证据仍可读取。
- 取消未启动请求不产生假的执行成功；已有执行须协调后按真实结果收尾。
- 两项待验收、一项未开始时主进度为 0/3；叶全部已验收但 root 未综合验收时明确显示差异。
- 既有 JSON/SQLite 历史、延迟读取与 HTML/XLSX 导出保持来源和边界。
