## 产品决策

建设一个在 Codex 内运行的任务规划、编排和进度插件：插件定义并校验任务流转、计算调度动作、维护执行与证据记录；通过 Codex 的执行能力落实规划决策、智能体派发、等待和结果回收。

**任务拆分、调度、分发列为必做，不能以“记录了 assignment”代替实际派发。** 全局 Planner 与叶任务内 Orchestrator 都要有明确的上下文、决策协议和运行状态；进度卡片呈现这一执行过程。早先“暂缓完整编排”的初步取舍由用户补充要求覆盖。

同时保留短任务的低开销路径：使用同一任务模型，按任务复杂度选择直接执行或进一步拆分，避免为了展示进度而增加无收益的模型调用和控制角色。

## 核心执行流程

1. **恢复或创建。** 调用方提交已确认的宿主标识和当前 conversation ID，映射到插件 session。新任务与恢复任务使用不同操作；新任务请求必须幂等。不能从 MCP 服务启动时的环境或工作目录推断所有调用都属于同一聊天。宿主不提供稳定身份时，仍允许显式 session ID。
2. **规划。** Planner 读取目标、需求、前驱结果及恢复上下文，提交 `execute` 或 `decompose` 决策。子任务分别携带目标、依赖、验收要求及需求覆盖声明。服务验证引用、环、兄弟关系、预算和覆盖声明的完整性；语义覆盖与任务质量由模型审查，不能声称图校验能证明正确性。
3. **选取可执行动作。** 调度引擎生成待规划、待派发、待回收或待综合动作。阶段内独立叶子组成执行批次；叶内报告可逐步驱动补充派发。资源声明不足时按保守串行处理，不假设不同节点天然隔离。
4. **认领与派发。** Codex 侧执行适配认领动作，再调用当前环境实际提供的协作/命令工具；工具返回后回填执行标识。任务 session、实例、epoch、node、attempt、assignment 必须一一关联。协作工具的可用模型、容量及权限来自当前环境，不硬编码。
5. **叶内决策。** 每个叶子的 Orchestrator 使用独立上下文和活动派发集合，选择继续调查、核验、等待或结束。逻辑角色必须分开；物理上可以由主会话轮流驱动或独立 agent 承担，不能让控制角色占满所有 agent 槽而使 worker 无法启动。
6. **回收与综合。** 接收有效报告，保存证据和缺口，更新执行状态；必要时继续派发。所有必要子任务结算后，父级综合并逐层传递。根任务的 resolved 必须有明确的验收依据，不能由计数自动产生。
7. **恢复或收尾。** 当前方案失败时，结算或停止相关执行，提炼有来源的事实、未解决关系和停止原因，进入下一 epoch；达到预算上限则输出当前证据与未解决要求。

第一套执行适配使用 Codex 的协作与命令工具。MCP 服务负责调度规则和状态事务，skill/执行适配负责持续消费动作并落实调用。外部执行使用通用身份、状态和能力协议，不依赖 Dagu；Dagu 只是当前开发工作区的命令路由约定或目标工作区可选服务，不是用户安装或核心发布前提。不能把已有 `get_ready_tasks → 写 assignment` 流程重新命名为“自动调度”便算实现。

纯 MCP 服务不会自行唤醒已经停止的 Codex 会话；第一版保证宿主执行循环活跃期间推进，停止后可以恢复。脱离宿主的常驻后台执行需要单独的执行器和生命周期支持，暂不列入首版承诺。

## 关键策略已经确定

- **保留多步骤自动跟踪和 HTN 数据模型。** 简单任务使用少量节点、直接执行和紧凑卡片，不再另造一套线性引擎。
- **依赖按含义区分。** 默认保留 `resolved`；研究证据传递可明确使用 `returned`，只接受正常结束的 resolved/open；failed/cancelled 不等同于返回了可用结果。旧 `finished` 策略保持可识别的兼容语义，不静默迁移。
- **规划与 workers 分层记录。** 独立目标进入 HTN 子任务；同一叶子内部的多次搜索、复核等进入 worker assignments/reports，不为了展示每次派发而改变任务分解。
- **实际能力决定运行模式。** 宿主缺少协作能力时，明确降级为主会话执行或等待适配；不能生成虚构 agent ID，也不能把缺少执行器的动作标记成功。
- **不能承诺外部派发恰好一次。** 外部创建成功但响应丢失时，记录派发结果未知，依靠关联标识与实际 agent 列表对账；未确定结果前不重复派发。
- **等待与失联分开。** 单纯长时间无更新只标“状态待确认”，不自动认定失败或停止外部执行；暂停也不能假装已经停止仍在运行的命令。
- **返工保留审计。** 第一批先拒绝不安全重试，后续通过显式重新打开分支作废旧验收、标记受影响下游待复核。历史 attempt 和证据保留。
- **用户授权和环境约束仍适用。** 调度资格不等于提交、推送、发消息或外部变更授权；工具路由、共享资源隔离和当前模型配置规则必须由执行适配遵守。
- **前端优先回答四件事。** 当前在做什么、为什么等待、下一步是什么、是否需要用户动作；完整树、派发细节和历史按需展开。

## 发布验收

1. **普通短任务：** 三个步骤可以低开销执行，明确综合验收；模型字段未知时仍可如实跟踪。
2. **结果驱动规划：** 前驱返回后，后续具体目标根据其证据生成；不能通过提前拆分绕过依赖。
3. **真实多智能体：** 至少一条实际派发链包含开始、等待、报告、一次针对性补充或核验、叶结果和父级综合；不能只用伪造 assignment 作为验收。
4. **调度约束：** 容量受限、共享资源冲突和前驱失败时均不误启动；活动工作已经覆盖缺口时不会重复派发。
5. **外部执行与解耦：** 使用当前可用的宿主执行工具，从真实 execution_id 核对运行与终止结果；有队列能力时区分排队与运行。未连接 Dagu 时核心编排仍可验收；Dagu 等服务集成作为可选专项，排队成功不能算测试成功。
6. **重试与恢复：** 模拟响应丢失、旧报告、宿主中断、新任务切换和重建，均不丢证据、不重复执行或错误标完成。
7. **历史与 UI：** 当前变更响应不携带全部历史；延迟卡片与乱序响应不倒退；旧版历史可查看和导出。
8. **预算：** 达到结构、并发、轮数或时间边界时正常结算并报告缺口，不扩大任务范围继续运行。

状态机和故障注入先使用临时存储与受控执行器，真实 Codex/宿主执行验收选择最小有意义场景。当前开发工作区中的测试与命令仍按其 `dagu-test-runner` 规则路由，该开发环境约定不构成插件产品依赖。
