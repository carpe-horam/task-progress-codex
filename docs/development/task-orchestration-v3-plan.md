## 1. 交付目标与执行顺序

完成从用户目标到规划、调度、真实分发、叶内协调、分层验收及带证据重建的完整链路。仅补进度卡片、提示词或 assignment 记录，不能通过核心编排验收。

按 **A → B → C → D** 交付。每批保持现有插件可启动、已有记录可读；B 和 C 都是必交范围。当前实现是可继续迭代的首轮基础，以下原定验收项仍未全部完成。

### 当前提交覆盖范围

- 已接入：SQLite 会话、任务、计划轮次、节点、attempt、assignment、action、result、evidence、event、request receipt 和 view；`task_open/read/advance/decide/report/control/history` 工具入口；基础幂等回执、scope 与 lease 检查；暂停/继续/取消请求、任务归档和旧 JSON 卡片兼容读取。
- 已接入界面：原位任务树详情显示每项摘要、产出、验收检查、未解决内容和证据；根节点摘要使用“整体说明”；保留“当前任务的历史计划”和“历史任务”分区。
- 仍待完成：稳健的旧 JSON 导入/备份迁移；真实 Codex agent 驱动器与跨会话容量/资源预留；完整 COLLECT/RECONCILE/STOP/PREPARE_REBUILD 动作生命周期；预算和上下文管理；分页卡片历史；导出新结果字段；迁移/异常恢复与并发/UI 实际验收。
- 因此该接口目前提供编排记录与宿主调用边界，不能单凭数据库内 assignment 声称 agent 已被真实派发，也不应将本轮描述为完整可发布实现。

产品核心不依赖 Dagu。首版以 Codex 执行驱动和通用外部事件协议交付，必须在未安装或未连接 Dagu 的环境中完成核心验收；特定队列服务的适配和集成测试按真实使用需求另行选择。

## 2. 开发约束和文件边界

- 复用当前工作区或已有合适 worktree，不嵌套创建。若以后明确采用并行开发，先分配下表中的文件归属；`server.py`、schema、API 和 skill 的共同改动串行集成。
- 状态和调度规则放在可隔离测试的 Python 领域模块；stdio 入口只做协议转换。优先标准库，测试也先用 `unittest`。
- SQLite 事务不得包含模型调用、真实派发或等待；所有外部执行经过持久化动作边界。
- 实际协作工具只能由 Codex 执行驱动调用；新 skill 说明允许使用工具的场景，不能覆盖更高优先级指令或自动授予外部修改权限。
- 在当前开发工作区执行命令和测试，继续遵循其 `dagu-test-runner` 约定：白名单或预计超过一分钟走 Dagu，其他短命令本地；必须走 Dagu 却不可用时停止该命令并说明原因。这是开发环境约束，不写入插件核心、默认用户工作流或通用 CI 的依赖要求。
- 真实用户进度文件不用作测试夹具；通过注入临时存储目录、时钟和 provider adapter 隔离。不得为跑测试清空用户历史。

| 文件组（拟新增模块见设计） | 修改职责 |
| --- | --- |
| models / graph / lifecycle | schema、图语义、attempt 生命周期、结果失效 |
| store / compatibility / api_v3 | 事务、迁移、幂等、版本与工具投影 |
| planner / scheduler / dispatch / orchestration | 决策验证、动作、资源、真实执行状态 |
| synthesis / recovery / context | 验收、来源、恢复证据和上下文预算 |
| app.html / views | 序号、按需读取、历史分页、实际控制状态 |
| skill / references / launchers / manifests | 宿主驱动协议、能力探测、安装与发布 |

依赖：A 批通过。

### DEV-B2：调度、容量和资源

依赖：B1；B3 使用此动作接口，不自行另建队列。

- 实现波次、PLAN/ORCHESTRATE/DISPATCH/COLLECT/SYNTHESIZE/STOP/RECONCILE/PREPARE_REBUILD 动作及明确阻塞原因。

- 工作区路径规范化，read 共享、write 排他；重叠目录、共享缓存和外部资源保守串行。跨 session 预留统一管理。

验收：T14～T16、T26。两个驱动争抢同一动作或资源时只有一个成功；满容量仍能回收、停止和对账。

### DEV-B3：真实派发、回收与对账

依赖：B2；与 B4 驱动协议串行集成。

- 实现 begin/confirm/reconcile；外部工具调用必须在 begin 已持久化后发生。

- skill 驱动调用当前宿主实际存在且允许的协作工具；缺失能力时返回阻塞或经过规则允许的主会话路径。
- 外部执行统一保存 provider/execution_id 与状态观察；由宿主工具映射，排队能力可选。服务专有定位字段放入 provider_metadata，核心不依赖 workflow/run 字段或特定 SDK；专用队列适配器不作为此项必做。

验收：T17～T21、E2。自动夹具之外，必须保存一条真实工具调用与返回标识链，不能只手写 assignment。

依赖：B3。

## 5. C 批：验收与恢复

### DEV-C1：分层验收与证据重建

依赖：B 批通过。

- 叶、父、根各有结果协议；父级记录独立 synthesis attempt、输入版本及逐项验收。
- 明确 resolved/returned/legacy_terminal，旧策略不悄悄改义。必要子项失败不通过正常综合绕过。
- 构造 supported_findings、unresolved_requirements、stop_reason、next_routes 和证据引用；未支持的猜测单独保留。
- 重建先结算外部执行，再原子创建新 epoch；新节点重新规划，旧证据可引用但不自动继承完成。

验收：T24、T25、E3、E4。必须能指出一个新计划实际使用的旧证据和一个仍未解决的要求。

### DEV-C2：暂停、等待与局部返工

依赖：C1 的结果版本和来源；重用 B3 对账。

- 实现 pause_requested/paused、waiting_user/waiting_external、interrupted；UI 读取不能刷新执行心跳。
- 实现待回答问题的身份/版本和 `answer_input`；只接受用户明确提交的答复，陈旧问题拒绝写入，范围变化走目标修订规则。
- 实现 reopen_branch 的影响闭包：旧结果消费者、祖先综合及其消费者；保留无关兄弟结果。
- 有在途/未知执行的受影响集合先收敛，不能直接改图；旧回报保留到旧 attempt，不覆盖当前结论。
- edit_plan 只修改未消费部分；范围变化有来源、需求修订及审计。

验收：T06、T11、T27、T28、E5。用户暂停后不再派发；未确认停止时不会提前释放资源或显示已取消。

### DEV-C3：上下文与预算

依赖：C1、C2；复用 B2 的计量，不另建一套计数器。

- 上下文按角色生成，携带根目标、祖先约束、前驱版本、相关来源和剩余额度；长内容用可读引用。
- 对输入生成 context_digest，旧决策不得基于已变化的报告/验收提交。
- 统一深度、分支、节点、并发、派发尝试、叶轮次、重建及墙钟预算；未知执行不退还预算。
- 达到预算只停止新工作，仍允许停止、回收、对账和证据收尾；保留未解决项。

验收：T23、T26、E4。无过度派发、无限重建或因预算耗尽而显示成功；约束不能被静默截断。

## 6. D 批：低开销使用与发布

### DEV-D1：短任务路径与历史体验

依赖：C 批通过；A5 已有基本紧凑读取。

- `task_open.initial_plan` 原子安装经验证的初始结构；`main_session_transition` 在实际观察基础上支持首次开始及 finish + start 事务。
- 快速路径仅适用于已明确可执行的主会话顺序任务；不得跳过规划、综合、独立核验或外部派发协议。
- 响应给出 next-ready；事件增量读取支持断档重同步；历史以 task/epoch/attempt 分层分页。
- UI 保留“当前任务的历史计划”和“历史任务”两个独立折叠入口：前者是同一实例的旧方案，后者是同会话此前创建的其他任务；旧任务自己的历史计划嵌套在其详情中。重规划不增加历史任务数，开启不同任务才归档原任务。分页与导出按类型、所属实例隔离。
- 卡片活跃时轮询、隐藏时停止、结束/长期等待时降频；展开才读取详细上下文与历史。
- 移除独立结果分区；任务项详情读取该节点产出、未解决事项和检查记录，根节点只呈现综合结论及定位链接。链接以 scope/result/evidence 引用绑定实际来源；历史节点使用冻结快照。按 UX-U06 验证不同节点入口、待执行空产出和最终综合未完成状态。

验收：T30、T31、E1、E6，性能目标见第 9 节。

### DEV-D2：数据恢复、导出与升级

依赖：A2 的基础迁移与 C 的完整 schema。

- 增加迁移预检、独立迁移命令、来源清单、只读恢复和一致性备份；大迁移不阻塞 MCP 启动握手。
- 保留最后有效快照；损坏记录报错并提供恢复入口，不默默创建空任务。
- JSON 机器可读导出保留身份/版本/来源；HTML/XLSX 基于同一快照生成，归档耗时冻结。
- 首版导入默认只读查看；若要继续，显式建立新任务和身份映射。v3 回滚不承诺旧版本能继续编辑新 schema。

验收：T29、T32、E6、E7；XLSX 的文件结构验证与真实 Excel 打开应分开记录。

### DEV-D3：安装、版本和使用说明

依赖：D1、D2。

- 目标最低 Python **3.10**；当前开发机实见 **3.12.10**。启动器先检查版本及 sqlite3 模块，再启动；不自动降级数据格式。
- 验证 macOS/Linux 的干净安装、升级、重载和 stdio；Windows 为独立兼容项，不因存在 cmd 启动器就宣称已支持。
- 同步 marketplace、plugin manifest、serverInfo、App appInfo、skill 和变更说明，发布包不能混合新旧契约。
- README 区分当前能力和新设计；给出简单任务、复杂开发、研究、暂停恢复四类用法及实际限制。

验收：T33、E7；发布说明列出实测 Python/OS/宿主、未验证项和恢复方法。

## 8. 真实使用场景验收

| ID | 场景 | 具体通过证据 |
| --- | --- | --- |
| E1 | 主会话完成三步小任务 | 初始计划/首项开始最多两次插件调用，后续顺序推进；不强制创建 worker；根有有效最终验收 |
| E2 | 隔离工作区中的修复与核验 | 真实 agent ID、任务/attempt/assignment 关联、等待和报告；一个缺口触发补充或 verifier；最后父级综合 |
| E3 | 前驱研究只得到部分答案 | open 正常返回后 returned 边可规划，resolved 边仍阻塞；后续细分引用新结果 |
| E4 | 初始路线失败后重建 | 明确记录为何旧计划失效及触发调整的证据/缺口；原因出现在被替换计划历史中；旧证据在恢复上下文可定位，新 epoch 重新规划；有限轮次后输出已知结果与缺口 |
| E5 | 宿主命令或其他可用外部执行期间暂停并恢复 | 保存真实 execution_id；暂停不新增工作；恢复先读取外部状态；具有队列能力时另验排队状态映射 |
| E6 | 同一聊天先整理读书笔记，再清理下载目录，后修复坐标轴并调整方案 | 前两个只在历史任务；修复旧方案只在当前任务的历史计划且历史任务数不增；旧任务各自计划不串入当前；新旧卡片不覆盖，展开/分页/导出与所选实例和轮次一致 |
| E7 | 从已有安装升级与恢复 | 原 JSON 备份/哈希、迁移结果、重载后的新旧读取、恢复演练；明确实测平台 |

E2 只在允许真实协作工具的宿主环境执行，使用无发布/发送副作用的隔离材料。自动 provider 夹具可验证错误路径，但不能代替 E2。真实 provider 无法稳定制造的丢失响应通过故障注入验证，并单独标注为模拟条件。

E1/E2/E5/E7 的核心链路须有未连接 Dagu 的真实环境验证。Dagu 等外部服务只在明确启用对应映射时增加专项验收，不能把其安装或在线状态作为插件核心发布门槛。queued 的异常路径可由通用 provider 夹具覆盖；特定服务集成结果单列。

每次验收保存：源码 commit 和工作区差异摘要、Python/SQLite/OS/宿主能力、操作或命令、真实执行引用、预期与实际、日志/截图/结果位置及限制。配置值与实际确认值分开记录。代码状态变化后，旧证据不直接算新版本通过。

## 9. 开销目标与运行矩阵

下面是新版本的验收目标，不是当前版本已经达到的指标：

- E1 的“初始计划 + 首项开始登记”最多两次插件调用；不把完整任务的规划、执行与验收宣称为总共两次调用。
- 默认变更回复不包含 task_history、完整 epoch 或报告原文；UTF-8 序列化响应目标不超过 **16 KiB**。超长摘要给出可展开引用，不截掉约束或证据来源。
- `task_history` 默认 20、上限 100 项；每页只返回所选层级。上下文默认 24,000 字符，并保留继续读取引用。
- 使用固定夹具（100 个历史任务、每个 40 个节点、每节点 5 条报告）测量默认回复大小和分页耗时；报告实际机器与重复次数，不把合成数据当真实用户分布。
- 不为首版编造 token/费用节省或毫秒级响应承诺；先记录基线与新版本的字节量、调用数和耗时。

| --- | --- | --- |

## 10. 升级与发布步骤

1. 完成 A 的夹具和兼容读取，准备 schema 1/2 的正常、非法和损坏样本。
2. 在临时目录完成迁移预检/失败恢复；对实际安装先盘点活动执行并结算，不直接停掉不明归属工作。
3. 重载旧服务，确认没有旧写入者后备份并导入；哈希/结构验证成功再切换 v3 写入。
4. 按 A、B、C、D 的退出条件验收，保留各自证据；A 可作为修复版交付，B/C 未通过前不宣布完整编排完成。
5. 运行最小发布组合：图与状态、幂等/崩溃、兼容迁移、实际编排 E2、返工/恢复、UI 排序、安装版本检查。
6. 更新同一发布包的版本和说明，列出未验证平台。发布、推送等外部操作仍按届时用户授权执行。
7. 若新版本读取异常，先保留新数据库与备份并进入只读恢复；不覆盖原 JSON，也不假设旧插件能编辑新数据。

开发顺序以依赖和退出条件为准，不以时间估算替代验收。任何精简范围若删除真实分发、叶内协调或带证据恢复，必须作为需求变更明确提出，不能悄悄降级为单纯的进度跟踪。
